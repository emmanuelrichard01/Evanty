01 — Product Requirements Document
Product Requirements Document

Problem statement

Existing event platforms — Lu.ma, Eventbrite, Meetup — are built around Stripe-only USD payments, have no Paystack or Flutterwave integration, no Naira or Cedi pricing, and no understanding of African event behaviour patterns: pay-at-door bank transfers, informal promoter networks, high mobile traffic on constrained connections, and low trust in foreign payment flows. Organizers in Lagos, Abuja, and Accra have no production-grade, locally-aware alternative.

→ This is a portfolio-grade production system, not a tutorial project. Every architectural decision should be defensible in a staff-level engineering interview.

Target market

Tech community managers, conference producers, workshop organizers, and cultural event hosts in Nigeria and Ghana. Secondary: their attendees, who are mobile-first and increasingly comfortable with digital payments via Paystack or Flutterwave but distrust foreign-branded checkout experiences.

Architecture decisions (ADRs)

ADR-001
PostgreSQL over MongoDB
Decision: PostgreSQL via Neon (serverless)
Events, ticket types, orders, order items, and tickets are deeply relational. MongoDB's document model is the wrong fit — every meaningful query requires JOIN-like $lookup aggregations. PostgreSQL provides native ACID multi-statement transactions (critical for the reservation flow), real foreign key constraints with cascades, CHECK constraints that enforce business rules at the database level (e.g. reserved + sold ≤ capacity), and pg_trgm for full-text search without a separate service.
Tradeoff: requires schema migrations via Drizzle Kit. More upfront design time. Better data integrity, honesty about domain shape.
ADR-002
Drizzle ORM over Prisma
Decision: Drizzle ORM
Drizzle generates explicit SQL that you can read and reason about. No n+1 query magic that hides behind abstraction. Lighter bundle, faster cold starts on Vercel Edge. Schema is defined as TypeScript objects, giving you full type inference in queries without a code generation step. Prisma is a valid alternative with a larger ecosystem, but for a portfolio project where demonstrating SQL literacy matters, Drizzle is the better signal.
Tradeoff: smaller ecosystem, less community tooling than Prisma. Acceptable for this scope.
ADR-003
Dual payment rails: Stripe + Paystack
Decision: Both PSPs behind a single checkout abstraction in the order service
Stripe handles international card payments and diaspora users. Paystack handles NG/GH domestic cards, bank transfers, and USSD. The organizer's account currency determines the default PSP; attendees can switch at checkout. The OrderService.createCheckout() method accepts a psp parameter and returns a redirect URL, keeping PSP logic isolated. Webhooks are verified separately per PSP signature method and converge on the same order confirmation handler.
Tradeoff: dual webhook handlers, dual SDK dependencies, dual reconciliation logic. Worth it for the market differentiation story.
ADR-004
BullMQ + Upstash Redis for async jobs
Decision: BullMQ with Upstash Redis (serverless-compatible)
Three categories of background work require a queue: reservation expiry (release inventory after 10-minute TTL), transactional emails (confirmation, reminders), and webhook retry logic with exponential backoff. Vercel serverless functions can't run persistent workers, so Upstash Redis provides the queue backend and a separate long-running worker process (deployed on Railway or Fly.io) consumes the queues. Upstash is pay-per-command with generous free tier.
Tradeoff: additional infrastructure component. Documented operational overhead is the honest cost of doing async jobs properly.
ADR-005
Cloudflare R2 over Uploadthing
Decision: Cloudflare R2 for event cover images and attachments
Uploadthing is convenient but abstracts too much for a senior portfolio project. R2 is S3-compatible, has zero egress fees, and integrating it directly demonstrates cloud storage literacy. File uploads go through a signed URL flow: client requests a signed upload URL from the server, uploads directly to R2, then sends the resulting object key to the server. Server stores the key, constructs the public CDN URL. Cloudflare Images handles resize/optimization on delivery.
Tradeoff: more implementation work. Worth it — demonstrates real cloud integration vs. third-party wrapper dependency.

Critical flow: atomic ticket reservation

This is the most important engineering decision in the entire system. The correct pattern is a database-level atomic update, not application-level inventory checking.

✕ Wrong pattern (tutorial-grade): SELECT current stock → check in application → if available, INSERT order. This has a TOCTOU race condition that will oversell tickets under concurrent load.
1
Client requests reservation
POST /api/v1/reservations — authenticated. Body: { ticket_type_id, quantity }
2
Atomic inventory update in a single SQL statement
The UPDATE and the check are one atomic operation. If capacity is already exhausted, the WHERE clause fails to match and 0 rows are updated — no reservation created.
UPDATE ticket_types
SET reserved = reserved + $quantity
WHERE id = $id AND (capacity - reserved - sold) >= $quantity
RETURNING id, (capacity - reserved - sold) AS remaining
3
Reservation record written with 10-minute TTL
A reservations row is inserted with expires_at = NOW() + INTERVAL '10 minutes'. A BullMQ job is enqueued with the same delay.
4
PSP checkout session created, client redirected
OrderService calls Stripe or Paystack, attaches reservation_id as metadata, and returns a checkout redirect URL. User completes payment externally.
5
Webhook received and verified
Stripe or Paystack POSTs to /api/webhooks/{psp}. Signature is verified with HMAC. On payment success event: reservation → confirmed order, inventory reserved decremented, sold incremented. Ticket rows and QR codes generated. Confirmation email enqueued.
6
Expiry worker handles abandoned reservations
BullMQ job fires at TTL. Checks reservation status — if still pending, sets to expired and runs: UPDATE ticket_types SET reserved = reserved - $quantity WHERE id = $id. Inventory released.

Service layer structure

Business logic is isolated from framework concerns. Services are plain TypeScript classes — no Next.js imports, no HTTP knowledge. This makes them unit-testable without spinning up an HTTP server.

03 — Database Schema
Database Schema & ERD

PostgreSQL. All monetary values stored in the smallest currency unit (kobo for NGN, pesewas for GHS, cents for USD) as BIGINT to avoid floating-point precision errors. All IDs are UUID generated via gen_random_uuid(). Timestamps are TIMESTAMPTZ.

! The ticket_types table contains a CHECK constraint reserved + sold ≤ capacity. This is the last line of defence against oversell — it enforces data integrity even if application-level logic fails.

04 — API Specification
API Specification

Base URL: /api/v1. All responses are JSON. Authentication via Clerk session cookie (web) or Authorization: Bearer <jwt> (mobile/API clients). All write endpoints validate input with Zod schemas before hitting the service layer.

→ Webhook endpoints at /api/webhooks/stripe and /api/webhooks/paystack are outside the versioned API. They use raw body parsing for signature verification and must never be behind authentication middleware.

Security & Pre-Deployment Checklist

Every item below must be verified before any public-facing deployment. Tick each only after you can demonstrate it works — not just that it is configured.

Authentication & authorization
Role-based access: owner / admin / member enforced in service layer, not just UI

MIME type validation server-side — not Content-Type header (spoofable)

Filename sanitised before storage — random UUID key in R2, never original filename

Load test: concurrency scenario

// k6 load test — concurrent reservation race
import http from 'k6/http';
import { check } from 'k6';

export let options = {
  vus: 100,          // 100 virtual users
  duration: '10s',   // all fire simultaneously
};

// Before test: create event with capacity = 50
// Expected: exactly 50 succeed (201), 50 fail (409 TICKET_SOLD_OUT)
// Zero orders with quantity > available. Zero DB constraint violations.

export default function () {
  const res = http.post('/api/v1/reservations', JSON.stringify({
    ticket_type_id: __ENV.TICKET_TYPE_ID,
    quantity: 1,
  }), { headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${__ENV.TOKEN}` } });

  check(res, {
    'status is 201 or 409': (r) => r.status === 201 || r.status === 409,
    'no 500 errors': (r) => r.status !== 500,
  });
}
! Do not launch to any real users until the k6 concurrent reservation test passes with zero oversells and zero 500 errors across 10 runs. This is the single most important quality gate in the entire project.

Runbook: ticket oversell incident

If a DB constraint violation is ever logged (should never happen with correct implementation):

1
Immediately pause event ticket sales
PATCH /events/:id with status: 'cancelled'. Prevents further orders while investigating.
2
Query actual state
SELECT id, capacity, reserved, sold, (capacity - reserved - sold) AS remaining FROM ticket_types WHERE event_id = $id
3
Reconcile orders vs inventory
Compare confirmed order count with sold counter. Any discrepancy indicates a counter drift bug.
4
Contact affected purchasers
Email all confirmed-order attendees within 1 hour. Offer full refund or waitlist position. Do not wait for them to discover the issue.
5
Root cause analysis + postmortem
Write a public (or at minimum documented) postmortem. What broke, when, why, what was done, what prevents recurrence.
